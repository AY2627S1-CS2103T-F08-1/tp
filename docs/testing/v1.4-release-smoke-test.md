# v1.4 release-candidate deletion smoke test (#69)

This checklist records reproducible manual checks for the v1.4 candidate JAR and its compatibility with data written by the v1.3 release. It follows the commands and index/ID distinction in the [User Guide](../UserGuide.md).

## 1. Prepare the candidate and a v1.3 data fixture

1. Check out the integrated release-candidate revision agreed by the team, including the #80 fix. Record the full commit SHA and confirm the working tree is clean. Build or obtain the candidate `osps.jar` from that exact revision. Keep the focused #69 evidence PR linked separately. Do not replace the candidate after recording its hash.
2. Record the OS and complete Java 25 version. Use the same candidate JAR and Java version for all cases.
3. Create a v1.3 fixture in a separate source folder using the official v1.3 release JAR. With no existing `data` directory, launch that JAR using `java -jar osps.jar`; the first run supplies the v1.3 sample debtors. Keep this folder separate from every candidate test folder.
4. In the v1.3 app, add three synthetic records with different balances. These provide non-zero amounts and distinctive names for the regression checks:

   ```text
   add n/Release QA Cedar p/81110001 e/release.qa.cedar@example.com a/1 Test Lane o/S$125.00 t/release-qa
   add n/Release QA Maple p/81110002 e/release.qa.maple@example.com a/2 Test Lane o/S$900.25 t/release-qa
   add n/Release QA Birch p/81110003 e/release.qa.birch@example.com a/3 Test Lane o/S$0.00 t/release-qa
   ```

5. Run `list`, record each persistent ID, displayed index, name, and amount, then add a note to Cedar and to one original v1.3 sample debtor using their IDs from the list. For example, replace `<CEDAR_ID>` and `<CONTROL_ID>` with the displayed IDs before entering:

   ```text
   note --id <CEDAR_ID> --text v1.3 fixture note for Cedar
   note --id <CONTROL_ID> --text v1.3 control note to preserve
   ```

6. Run `show --id <CEDAR_ID>` and `show --id <CONTROL_ID>` to confirm each note. Close the v1.3 app with `exit`. Preserve the source `data/addressbook.json`; record the v1.3 release URL/version, source JAR hash, fixture file hash, record count, and baseline inventory in the manifest. Use synthetic or otherwise approved test data only.
7. For each candidate case, create a new isolated folder, copy in the same candidate `osps.jar`, and copy the preserved v1.3 `data` folder into it. This gives every destructive case the same baseline. Also create one empty folder with only the candidate JAR for the clean-folder launch case. Never use the v1.3 source folder for candidate testing.

## 2. Clean-folder launch

1. From the empty candidate folder, run `java -jar osps.jar` with Java 25.
2. Confirm the app opens and shows its first-run sample data. Run `list` and capture the output/screenshot.
3. Close the app with `exit`. Record pass/fail and evidence. This checks startup in a clean folder; it does not replace the v1.3-data compatibility case below.

## 3. End-to-end v1.3-data workflow

Use a fresh candidate folder populated from the preserved v1.3 fixture.

1. Launch the candidate with `java -jar osps.jar`. Run `list`; compare IDs, names, amounts, and counts with the fixture baseline. Run `show --id <CONTROL_ID>` and confirm the pre-existing control note is present.
2. Add a candidate-only debtor:

   ```text
   add n/Release Smoke Target p/81110004 e/release.smoke.target@example.com a/4 Test Lane o/S$1,250.00 t/release-smoke
   ```

   Record the new persistent ID from the result/list. Run `list` and confirm the new record and amount.
3. Run `find Release Smoke Target`. From that filtered result, record the displayed index and persistent ID. Run `show --id <TARGET_ID>` and confirm the displayed profile belongs to the same debtor.
4. Add an interaction note and verify it with `show`:

   ```text
   note --id <TARGET_ID> --text Candidate smoke note before deletion
   show --id <TARGET_ID>
   ```

5. Edit the currently displayed target by its current displayed index. The value must come from the latest filtered list, not from its persistent ID:

   ```text
   edit <TARGET_INDEX> a/4 Updated Test Lane
   ```

   Run `show --id <TARGET_ID>` and confirm the address changed while the ID, amount, and note remain correct. Run `find Release Smoke Target` again and confirm the target is still in the filtered list.
6. Run `delete <TARGET_INDEX>` using the index shown by that latest filtered result. Confirm the success message names **Release Smoke Target** (with the correct edited address/details), the filtered view refreshes, and the target ID is absent. This is the filtered-index and profile-identity acceptance check.
7. Run `list`; compare every original v1.3 record against the baseline. All original IDs, names, amounts, and notes must remain unchanged. Confirm `show --id <TARGET_ID>` reports that no active debtor with that ID exists.
8. Close the app with `exit`, relaunch the same candidate JAR in the same folder, and run `list` and `show --id <CONTROL_ID>`. Confirm the deletion persisted and all surviving IDs, amounts, and notes still match the baseline. Capture before-delete, deletion-result, after-delete, and post-restart evidence.

## 4. Displayed-index positions and selected profile

Run each case in a fresh copy of the same v1.3 fixture folder so that each starts from the identical baseline.

| Case | Procedure | Pass condition |
| --- | --- | --- |
| First | Run `list`; identify the debtor shown at displayed index `1`; run `show --id <THAT_ID>`, then `delete 1`. | The message identifies the index-1 debtor; exactly that ID disappears. |
| Middle | Run `list`; choose the middle displayed row (for an even count, use the lower middle); show its persistent ID, then delete that displayed index. | The message identifies that row; exactly that ID disappears. |
| Last | Run `list`; record the final displayed index and ID; show that ID, then delete the final index. | The message identifies the final row; exactly that ID disappears. |
| Filtered/profile | Run `find Release QA`; record the filtered rows and their current indexes; use `show --id <TARGET_ID>` for the intended debtor, then delete the index shown beside that debtor in the filtered result. | The success message names the same debtor shown by `show`; the filter remains active and only the intended ID is removed. |
| Only | In a separate clean candidate folder, run `clear`; add exactly one synthetic debtor; run `list`, `show --id <ID>`, and `delete 1`. | The only debtor is removed, the empty-state message is shown, and `show --id <ID>` reports no active debtor. |

For every case, save the pre-delete inventory and compare the post-delete inventory. All surviving IDs, amounts, notes, names, and other records must remain unchanged. `show --id` takes a persistent ID; `delete` takes the one-based index from the current displayed list.

## 5. Invalid and oversized indexes

Run each command against a fresh fixture copy or restore the exact same baseline before the next command. After each rejection, run `list` and inspect the data file or restart the app to confirm no record changed.

| Input | Expected result |
| --- | --- |
| `delete` | Usage/format error; no deletion. |
| `delete abc` | Usage/format error; no deletion. |
| `delete -1` | Usage/format error; no deletion. |
| `delete 0` | Usage/format error; no deletion. |
| `delete 1.5` | Usage/format error; no deletion. |
| `delete <COUNT_PLUS_ONE>` | Out-of-range error reports the current displayed count/range; no deletion. |
| `find NoSuchReleaseSmokeDebtor`, then `delete 1` | Out-of-range/empty-result error; no deletion. |
| `delete ` followed by 101 `9` digits | Rejected as out of range promptly; no hang, crash, or deletion. Error feedback may abbreviate the index and should indicate its digit count. |
| `delete ` followed by 1,000,000 `9` digits | Repeat #80's stress case on both a populated and empty displayed list. Record elapsed response time and continued UI responsiveness; feedback stays bounded and data is unchanged. |

Generate the million-digit command in a file using PowerShell (`Set-Content -NoNewline -Path delete-stress.txt -Value ('delete ' + ('9' * 1000000))`), then paste its contents into the candidate's command box. Record any UI input limit or paste failure separately; do not mark the stress case passed if the full input did not reach the app. In a disposable fixture copy, also check `delete 0001` deletes the first displayed debtor and `delete 0000` is rejected without changes.

Record the exact observed feedback for malformed, non-positive, out-of-range, and very large cases. Confirm the same baseline IDs, amounts, and notes remain after restarting at least once.

1. Before the manual run, calculate and record the candidate `osps.jar` SHA-256. On PowerShell, use `Get-FileHash .\osps.jar -Algorithm SHA256`; on macOS/Linux, use `shasum -a 256 osps.jar` or `sha256sum osps.jar`.
2. Run all smoke cases against that exact file. Record the hash and full commit SHA beside the test results and screenshots.
3. After the release asset is uploaded, download the uploaded `osps.jar` without renaming/repacking it. Calculate its SHA-256 with the same method and compare it to the tested candidate hash.
4. Mark the release-asset comparison **PASS** only when the full hashes match. A missing upload, unavailable asset, or mismatch remains **PENDING/FAIL**; it is not evidence that the uploaded release is the tested JAR.
